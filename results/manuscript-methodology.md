## Docker-based experimental methodology

A containerized proof-of-concept was implemented to measure the complete cross-domain authorization and session-establishment path. The testbed comprised four independently deployed services: Gateway A, Gateway B, a logically centralized Session Authorization Controller (SAC), and an off-path ledger adapter. Services communicated through a Docker bridge network. The implementation used ML-KEM-768 for gateway-to-gateway key encapsulation, HKDF-SHA-256 for session-key derivation, Ed25519 for SAC signatures, AES-256-GCM for confidential provisioning of SAC authorization inputs, and HMAC-SHA-256 for explicit key confirmation.

Gateway A initiated each experiment by generating a fresh nonce and sending an authorization request to the SAC. The SAC evaluated the requested action, generated a session identifier and session-scoped authorization inputs, constructed and signed the session context and capability claims, and confidentially provisioned equivalent authorization material to both gateways. After validating the SAC-issued material and the cached ledger epoch, Gateway A encapsulated an ML-KEM shared secret using Gateway B's pre-provisioned public key. Gateway B decapsulated the ciphertext, and both gateways independently derived the session key. Gateway B then generated a transcript-bound confirmation MAC, which Gateway A verified before declaring the session usable.

The authoritative end-to-end timer used Python's monotonic nanosecond-resolution performance counter. The timer began immediately before Gateway A transmitted the SAC authorization request and stopped after Gateway A successfully verified Gateway B's key-confirmation MAC. Thus, the measured interval included SAC processing, inter-container transport, authorization provisioning and verification, ML-KEM encapsulation and decapsulation, HKDF execution, key confirmation, serialization, scheduling, and gateway processing. Ledger submission and confirmation were excluded because commitment processing began only after the session became usable.

Before each measured trial, 100 warm-up requests were executed to reduce initialization and connection-establishment effects. Five independent trials were conducted at each concurrency level. The concurrency-1 E2E evaluation used 1,000 measured sessions per trial. Reported confidence intervals are two-sided 95% Student's t intervals calculated across the five independent trial-level estimates.

At concurrency 1, the SAC-inclusive authorization-to-usable-session latency was 2.1684 ± 0.0939 ms, with a p95 latency of 2.8499 ± 0.3801 ms. The authorization path accounted for 1.3773 ± 0.0636 ms. Cumulative gateway cryptographic processing, including authorization verification at both gateways, ML-KEM, HKDF, and MAC processing, was 0.3223 ± 0.0137 ms. This cryptographic-processing value is not an end-to-end wall-clock interval and is therefore reported separately.

SAC scalability was evaluated independently using five trials of 2,000 measured authorization requests per concurrency level after 100 warm-ups. The measurement included policy evaluation, context construction, signatures, encrypted authorization provisioning, and Gateway B verification. The highest observed throughput was 1,365.14 ± 17.15 authorizations per second at concurrency 5, with client-observed mean and p95 latencies of 3.600 ± 0.045 ms and 5.799 ± 0.190 ms, respectively. Throughput declined and latency increased beyond concurrency 5, locating the observed saturation knee between concurrency 5 and 10. At concurrency 100, client-observed p95 latency reached 981.655 ± 144.247 ms despite zero application-level failures, showing that queueing latency, rather than request rejection, defined overload.

The Docker ledger adapter used simulated finality to verify that ledger processing remained off the session-establishment path. Consequently, simulated ledger-finality values are not presented as live IOTA measurements. Historical Shimmer measurements, if retained, must be labeled as results from a separate implementation and experimental environment. The Docker bridge also represents a same-host deployment; geographically distributed industrial-domain latency was not emulated in these experiments.
